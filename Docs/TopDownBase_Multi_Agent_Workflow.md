# TopDownBase — AI 협업과 문서 운영 원칙

> **목적:** AI 간 책임을 분리해 서로의 실수를 발견하되, **개발자가 이해하고 설명할 수 있는 코드**를 남긴다. 이 문서는 초기 협업 구조의 기준이며 세부 기능 설계·개발 지시서는 아니다.

## 1. 역할 분담

| 담당 | 핵심 책임 | 사용 시점 |
| --- | --- | --- |
| **전체 기획 채팅** | 게임의 전체 방향·우선순위와 협업 구조 정리 | 전체 기획과 기능 간 방향을 결정할 때 |
| **Codex** | 세부 기술 계획, Unity 메인 구현·디버깅·검증 | 기능별 개발 채팅에서 구현까지 책임 |
| **Claude Code** | 독립 기술 설계 검토, 코드 QA, 복합 버그 분석 | 위험이 큰 기능 또는 통합 시점 |
| **Claude Chat** | 게임성·플레이 경험 독립 평가 | 재미나 방향을 재검토할 필요가 있을 때 |
| **개발자 본인** | 기능 요구 확정, 코드 이해, 실제 플레이 테스트, 최종 승인 | 모든 핵심 의사결정과 구현 단계 |

## 2. 프로젝트 내 공통 지침

```text
TopDownBase/
├── AGENTS.md                       # 공통 원칙·역할·권한
├── CLAUDE.md                       # Claude Code 검토 규칙
├── PROCESS.md                      # 전체 개발 과정
├── .agents/skills/implement-feature/SKILL.md
├── .claude/skills/review-feature/SKILL.md
└── Docs/
    ├── TopDownBase_Initial_Game_Plan.md # 기획 기준
    ├── TopDownBase_Plan_Writing_Guide.md # 계획·과정 문서 작성 원칙
    ├── TopDownBase_Multi_Agent_Workflow.md # 이 협업·문서 운영 기준
    ├── AGENT_PROMPTS.md            # 필요 시 사용하는 프롬프트
    ├── Features/<분야명>/Process.md # 분야별 목표와 기능 현황
    └── Features/<분야명>/<기능명>/ # 필요한 기능별 계획·과정·인계 기록
```

분야·기능 폴더와 `AGENT_PROMPTS.md`는 필요해질 때 만든다. 문서 경로와 역할은 다음과 같다.

| 문서 | 역할과 작성 시점 |
| --- | --- |
| `AGENTS.md`, `CLAUDE.md` | 각각 Codex 공통 작업 원칙과 Claude Code 독립 검토 원칙 |
| `.agents/skills/implement-feature/SKILL.md` | Codex의 기능 조사·구현·검증·인계 절차 |
| `.claude/skills/review-feature/SKILL.md` | Claude Code의 독립 기능 검토 절차 |
| `PROCESS.md` | 전체 개발 목표, 분야별 현황과 다음 단계 |
| `Docs/TopDownBase_Plan_Writing_Guide.md` | 작업 계획과 계층형 과정 문서의 작성·갱신 원칙 |
| `Docs/Features/<분야명>/Process.md` | 분야별 목표·기능 현황·의존 관계. 해당 분야 작업을 시작할 때 작성 |
| `Docs/Features/<분야명>/<기능명>/Process.md` | 기능별 단계·이유·상태와 개발자 확인 결과. 기능 작업을 시작할 때 작성 |
| 기능 폴더의 `Plan.md`, `Handoff.md` | 필요한 경우 각각 기능 계획과 다른 세션·에이전트용 인계 기록 |
| `Docs/AGENT_PROMPTS.md` | 반복 프롬프트가 실제로 필요할 때 작성 |

공통 지침에는 항상 적용할 원칙을, 스킬에는 해당 작업에서 반복할 절차를 둔다. 게임 기획과 결정은 `Docs/`에 기록하고 스킬에 복사하지 않는다. 사용자의 명시적 지시와 실행 환경의 상위 지침이 우선한다.

- **에셋 원본 보호:** TopDown Engine 등 외부 에셋의 원본 코드·데모 씬·프리팹은 직접 수정하지 않는다. 프로젝트 소유 코드·프리팹 복제·Variant로 확장한다.
- **작은 구현:** 기능 수와 설계 복잡도보다 조작감·안정성을 우선한다.
- **근거 중심:** 엔진 지원 여부와 테스트 성공은 실제 코드와 Unity 실행 결과로 구분한다.

## 3. 채팅 운영과 작업 인계

1. **Codex는 기능별 새 채팅**에서 작업한다. 기능이 완료될 때까지 같은 채팅을 유지한다.
2. Codex는 구현 전에 **목적·재사용할 기능·변경 파일 예상·검증 방법**을 짧게 설명한다. 이미 주어진 지시와 권한 범위에서 진행하며, 요구가 불명확하거나 실제 권한이 필요한 결정은 확인한다.
3. 구현 후에는 **무엇을 왜 바꿨는지**, 핵심 코드 흐름, 실제 검증과 미검증 항목을 설명한다.
4. Claude Code는 중요한 기능에서 **실제 코드·변경 내역**을 독립적으로 검토한다. 게임 코드는 기본 읽기 전용이고 필요하면 관련 문서에 QA를 남긴다.
5. 개발자는 AI 결과를 직접 실행·관찰하고, 이해되지 않는 코드와 설계는 설명을 요구하거나 수정한다.

**작업 인계는 가능한 한 프로젝트 파일과 짧은 MD 기록을 활용한다.** ChatGPT·Claude Chat의 로컬 폴더 접근은 연결 여부가 확인되기 전까지 가정하지 않는다. 자동으로 AI끼리 호출하는 별도 시스템은 구축하지 않는다.

전체 기획 채팅에서 정한 목표·완료 조건·범위와 참고 문서를 기능 채팅에 전달한다. 기능별 과정 문서에 진행과 검증을 기록하고, 상태가 바뀌면 분야와 전체 과정의 요약도 갱신한다. 새로 확정할 게임 규칙은 개발자의 판단을 거쳐 기획서에 반영한다.

### 분야별 완료와 Git 커밋

- 분야에 정해진 기능과 완료 조건이 충족되고 필요한 검증 및 개발자의 확인이 끝나 해당 분야가 완료되면 커밋한다. 개별 기능이 끝났다는 이유만으로 분야 전체가 완료된 것으로 간주하지 않는다.
- 커밋 전 분야·기능 과정 문서와 전체 과정 요약을 실제 결과에 맞게 갱신하고, Git 상태와 변경 내용을 확인한다. 검증하지 못한 항목은 완료로 기록하지 않는다.
- 해당 분야 작업에 속하는 코드·에셋·Unity 메타 파일과 관련 문서만 선택해 스테이징하고, 내용을 설명하는 커밋 메시지로 커밋한다. 기존의 무관한 변경이나 다른 작업자의 변경은 포함하거나 덮어쓰지 않는다. 같은 파일에 관련 변경과 무관한 변경이 섞여 분리할 수 없으면 무리해서 커밋하지 말고 상황을 보고한다.
- 커밋 결과와 해시, 검증 결과 또는 커밋하지 못한 이유를 사용자에게 알린다. 원격 저장소에 푸시하는 작업은 별도 지시가 있을 때만 수행한다.

## 4. 개발자 중심 품질 게이트

| 단계 | 개발자가 확인할 것 |
| --- | --- |
| 구현 전 | 왜 필요한 기능인지, 기존 엔진으로 대체 가능한지, 변경 범위가 작은지 |
| 구현 직후 | 직접 수정된 파일과 핵심 함수의 역할을 설명할 수 있는지 |
| 실행 테스트 | 재현 방법과 정상·실패 조건을 스스로 확인했는지 |
| 독립 검토 | Claude의 지적이 실제 근거를 갖는지, 수정이 꼭 필요한지 |
| 최종 승인 | 기능이 의도대로 동작하고 다른 기능에 영향을 주지 않는지 |

**기억할 원칙:** AI가 “완료”라고 보고한 것과 개발자가 **이해하고 검증해 승인한 것**은 다르다. 하나의 기능을 설명하지 못한 채 다음 기능으로 넘어가지 않는다.

## 5. 재설계 이유와 기대 효과

초기 시도에서는 세부 설계와 구현 지시까지 AI에 크게 의존해 개발자가 코드의 동작 원리와 판단 근거를 따라가기 어려웠다. 전체 기획과 기능별 구현을 나누고 Codex·Claude의 역할을 기능 단위로 분리해 판단 근거를 따라갈 수 있도록 한다.

목표는 AI가 더 많은 결과물을 만들게 하는 것이 아니라 **개발자가 요구사항을 판단하고, 코드를 이해하고, 직접 테스트하며, 문제를 설명할 수 있는 개발 역량을 기르는 것**이다.

## 6. 스킬 운영

- `implement-feature`는 기능 목표와 기존 엔진의 실제 지원을 조사하고, 작은 변경을 구현·검증하며 개발자가 이해할 수 있도록 결과를 설명한다.
- `review-feature`는 실제 요구사항과 변경 내용을 독립적으로 확인하고, 근거·영향·위치와 실행 여부를 포함해 발견 사항을 보고한다. 게임 코드는 기본 읽기 전용으로 검토한다.
- 두 스킬은 각 실행 환경의 별도 경로에 있으므로 한쪽이 다른 쪽에 자동으로 적용된다고 가정하지 않는다. 스킬 작성 시 각 환경의 형식과 검색 경로를 확인한다.
- 기능별 스킬을 미리 늘리지 않는다. 반복 작업에서 프로젝트 고유 절차가 드러나고 기존 스킬로 충분하지 않을 때 추가한다. 일회성 기획과 체크리스트는 관련 기능 폴더에 둔다.
